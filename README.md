# Agentic ETL Pipeline Failure Investigator

## The Problem
**Who has it:** Data engineers and data platform teams.
**The bottleneck:** When a production ETL pipeline fails (often at 3 AM), the context needed to debug is scattered across execution logs, schema definitions, row count metrics, and source systems. Engineers spend 2-4 hours doing manual, repetitive investigation—correlating log timestamps, diffing schemas, and checking data quality constraints—just to identify the root cause before they can even start fixing it.

## The Solution
An agentic workflow that automatically investigates pipeline failures by coordinating specialized agents to parse logs, compare schemas, validate data quality, and synthesize a structured Root Cause Analysis report with actionable remediation steps.

## Architecture
Built using **LangGraph** for stateful multi-agent orchestration and **FastAPI** for serving. The system leverages specialized deterministic tools (Log Parser, Schema Comparator, Data Validator) combined with LLM agents (GPT-4o) for semantic reasoning. A critical **Verification Layer** acts as a human-in-the-loop proxy, ensuring reports are actionable before delivery.

**Why LangGraph?** Unlike a single-prompt RAG approach, LangGraph stateful orchestration allows the system to dynamically route the investigation based on intermediate findings. For instance, if the Log Agent finds no schema-related errors, the Schema Agent is skipped entirely, significantly reducing token cost and latency.

## Hot Take / Insights
**Verification > More Agents.** I initially planned to build 7 different specialist agents. However, I found that adding a verification layer at the end of the RCA generation—which simply checks if the output contains specific evidence and actionable steps—improved the output quality dramatically. The LLM is capable of deep analysis, but it needs a strict checklist to format that analysis usefully. One verification step improved output quality more than adding another specialist agent would have.

**The Limits of the Architecture (Scenario 10).** The complex multi-failure scenario returning "Partial" is a valuable lesson. The pipeline failed due to both a schema drift and a subsequent downstream API timeout. The agents accurately diagnosed the schema drift but stopped deep analysis there, missing the secondary infrastructure failure. This revealed that the orchestration routing is currently too greedy—it stops at the *first* critical failure rather than exhaustively investigating the entire pipeline lifecycle.

**Real World Application.** The system was validated on 10 synthetic scenarios designed to mirror real production failure patterns.

**Current Known Limitation:**
The system achieves 95% accuracy on 10 structured synthetic scenarios. Real production logs contain unstructured error messages, mixed encoding, partial stack traces, and vendor-specific formats that our structured log parser does not yet handle gracefully.

Validating against live production logs from real pipelines is the confirmed next step. We expect accuracy to drop to 70-80% on noisy real-world data before parser improvements are applied.
